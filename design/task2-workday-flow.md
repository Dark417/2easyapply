# Workday (`myworkdayjobs.com`) Auto Apply Flow

## Purpose

Eve supports Workday application URLs whose hostname contains `myworkdayjobs.com`. Workday is implemented as an isolated platform adapter so its selectors, navigation, and step logic cannot interfere with LinkedIn Easy Apply.

## UI contract

- Reuse the floating Eve panel styling, but keep Workday information in its own store.
- **The panel shows on every `myworkdayjobs.com` page** (`isWorkdayPage()`), not only `/apply` pages — login, job listing, and search pages included. The content script already matches `*://*.myworkdayjobs.com/*`; UI injection and boot are host-gated, not `/apply`-gated.
- **Login/auth pages**: on a `/login` path (or a rendered Create Account / Sign In screen), clicking **Apply** / **Auto Apply** triggers **Sign in with Google** (`handleWorkdayLogin()`) with the configured account. This is the sole explicit-user auth exception for Manual mode; other pre-flow entry (Start-page Autofill-with-Resume, email/create-account) still is not entered by Manual.
- Show only `Apply`, `Step`, and `Info`; Workday has no Eve job-search tab.
- Every newly loaded Workday document lands on `Apply`, and **the flow stays on `Apply` throughout — it never auto-switches to `Step` or `Info`** (not on Auto Apply start, pause, or Manual fill). Status shows on `Apply` via `setStatus`; `renderStep` keeps the Step tab's contents current in the background. The Step/Info buttons still switch on user click; a prior selection is never restored on a fresh landing.
- `Apply` contains a persisted Auto switch and a mode-aware action button. When Auto is on, the button reads **Auto Apply** and an explicit click starts/resumes end-to-end filling and navigation. When Auto is off, the button reads **Apply** and an explicit click fills the current step and then clicks its one advance action (Continue / Save and Continue / Next / Review), advancing exactly one step and stopping on the next. It never auto-submits at Review (Submit needs explicit approval) and never authenticates. Toggling modes never starts either action by itself.
- The action click commits the mode currently shown by the Workday toggle before dispatching Manual or Auto behavior. This prevents an immediate **Auto Apply** click from re-reading a stale `manual` value while the toggle's asynchronous storage write is still pending.
- `Step` reports the detected Workday step and its visible editable fields.
- `Info` reads and edits `workdaySavedAnswers`, which is separate from LinkedIn `savedAnswers`.
- Keep the panel readable in both dark and light themes.

## Automation pacing

- **No general delay (user, 2026-07-18).** `ACTION_DELAY_MS = 0`: clicks, picker choices, checkbox/radio changes, and programmatic field sets execute immediately. Correctness comes from the picker code already **polling/waiting for options to render** (`waitForOptionMatching`, `waitForButton`, `waitForPrecedenceOption`, `MutationObserver`), not from a fixed pre-delay. There is no artificial spacing in the job flow.
- **The only deliberate wait is the long search-result pickers** — **Field of Study** (and a searchable **School** list where a tenant uses one): after typing the search term, wait `PICKER_SEARCH_SETTLE_MS = 500` ms for the filtered results to come back, then select as soon as a match appears (the precedence poll still covers slower results up to its own timeout). These are the "long list, only a few real matches" fields the user called out. Everything else has zero delay.
- Historical note: this supersedes the former 2 s (later 250 ms) global spacing. The status line no longer says "(2s safety delay)"; it just shows the action.
- The applicable mode/capability and extension-enabled flag are rechecked immediately before each interaction. Turning Auto off cancels an Auto session; invalidating a Manual pass expires its one-shot resume capability and prevents an already-scheduled click.
- DOM observation may poll faster because observation itself is read-only and does not interact with the site.

## Generic step advance

- `advanceWorkdayStep(context, options)` is the single repeatable/callable primitive for Workday Continue, Next, Save and Continue, and Review actions.
- Every call rechecks the shared automation gate (extension enabled, matching mode, active pass for Manual or active session for Auto) and re-resolves the live footer button. Both Auto and Manual are accepted; the primitive resolves the current step's supported advance label (Continue / Next / Save and Continue / Review). Submit is always rejected regardless of mode.
- It waits the shared two-second interaction delay, clicks exactly once, and resolves only after the pathname/active-step/visible-form signature changes. Callers may invoke it again on a later step; stale button nodes are never reused. Auto loops through repeated calls; Manual invokes it once per **Apply** click and stops on the resulting step.
- Resume handling invokes it only after confirmed in-place upload in either mode. Manual stops on the resulting step; Auto may keep looping. A tenant-owned parser transition counts as the step change and suppresses a redundant Continue click.
- Resume-upload confirmation is independent from footer readiness. Once Workday visibly confirms the file, the generic primitive waits for a later-rendered enabled footer action itself; the resume handler does not require the button to exist at the same instant as the success message.

## Manual current-step mode

- Manual mode is selected when `eveApplyMode` is `manual`; it is not a disabled UI state while Eve itself remains enabled.
- Clicking **Apply** fills the currently rendered Workday form and then clicks its one advance action (Continue / Save and Continue / Next / Review), advancing exactly one step and stopping on the newly rendered step. Filling populates text, picker, radio, and checkbox answers using the same first-party answer resolution and two-second interaction spacing as Auto mode. The only per-step difference from Auto is that Manual stops after one advance while Auto keeps looping.
- On **My Information**, the fill pass merges stable packaged profile defaults with `workdaySavedAnswers`; previously saved non-empty Workday values win. Each explicit Manual **Apply** force-refills every known blank while preserving already-valid values, a fresh or empty runtime cache must not leave known identity, address, or phone fields blank, and it then clicks **Save and Continue** to reach the next step.
- The manual pass must not enter the pre-flow application, authenticate, open a local file chooser, auto-submit at Review (Submit needs explicit approval), or persist a running session. After clicking its one advance action it stops and does not react to later DOM/navigation changes.
- Switching from Auto to Manual cancels the active loop first. A later Manual **Apply** click is a new single-step action, never a continuation of the former loop.
- **Autofill with Resume is a fillable step**: the extension retrieves `artifacts/Xiaoxiao_Lei_RESUME.pdf` through an allowlisted background message and assigns it to Workday's real file input with `DataTransfer`; no chooser or document UI is shown. After confirmed upload, Manual **Apply** clicks Continue and stops on the next step; Auto **Auto Apply** may continue its loop.
- Cover-letter inputs are matched separately and receive `artifacts/Xiaoxiao_Lei_Cover_Letter.pdf`. The background endpoint exposes only these two logical artifact IDs and never publishes the PDFs as web-accessible resources.
- A tenant may implement resume upload as a pre-step that automatically swaps the page to **My Information** when parsing finishes. This is a Workday-owned state transition, not a Continue click. Manual mode reports the transition and stops; it never fills the newly rendered step in the same Apply pass.

Workday renders many step controls asynchronously. After every navigation, the adapter keeps the exact application session active and uses a `MutationObserver` with a 200 ms polling fallback for up to 15 seconds. Authentication gets a dedicated Google-only wait, so an email button rendering first cannot trigger the fallback. **Sign in with Google** is clicked as soon as Workday makes it available instead of treating the first empty DOM check as a blocked step.

## Re-authentication after inactivity logout

- Workday logs out long-idle sessions and re-renders the same `/apply/...` URL as the **Create Account/Sign In** screen. `isAuthenticationScreen()` recognizes it from the step label `Create Account / Sign In`, the `Sign in with Apple`/`Sign in with email` buttons, or the `Privacy Notice` text.
- On this screen the progress bar shows a future **Autofill with Resume** step label. The Auto Apply loop must not treat that label as the entry button: while `isAuthenticationScreen()` is true the loop skips the Autofill-with-Resume entry click and routes straight to the login flow (**Sign in with Google** → configured account → return → resume the running session). This is a hard, deliberate contract — landing on the login page never auto-starts; the user still clicks **Auto Apply** once.
- The Google account chooser helper accepts an OAuth request that returns to any Workday-owned host — `myworkday.com`/`*.myworkday.com` and the tenant application host `myworkdayjobs.com`/`*.myworkdayjobs.com` (e.g. `blackrock.wd1.myworkdayjobs.com`) — with basic `openid`/`email`/`profile` scopes only. With an existing Google session the provider completes silently; when a chooser appears the helper selects the configured job-application account under the same session/mode gates and two-second spacing.

## Authentication safety

- The Google helper runs only on `accounts.google.com` when the OAuth callback or application domain ends in `myworkday.com`.
- It accepts only basic `openid`, `email`, and `profile` scopes.
- It never reads passwords and only chooses the configured job-application Google account.
- `.env` credentials remain local developer data. Chrome content scripts cannot read the project filesystem, so credentials must never be copied into manifest, source, logs, design docs, or packaged assets.
- If a tenant lacks Google sign-in, the adapter chooses Create Account when visible, otherwise opens Sign in with email. A rendered Create Account form is distinct from its opener: the adapter never clicks an empty submit form. It pauses for secret-safe local `.env` entry and required privacy/terms consent, then the same Auto Apply button can submit the ready account form after rechecking the automation gates.
- **Email/password tenants with no Google option (e.g. T-Mobile)**: a returning applicant lands on a plain **Sign In** form (email + single password) rather than Create Account. `isSignInForm()` recognizes it (one visible password field + an in-`main` **Sign In** button, and not a Create Account form) and is distinct from `isCreateAccountForm()`, which now requires **two** password fields (the Verify New Password field) so the Sign In page's own "Create Account" link no longer misidentifies it. On Sign In, Auto Apply submits **only when the user has already filled the password locally** (`signInFormReady()`); it never types the password. The Sign In check runs **before** Create Account in the Auto loop so an existing account is signed into, never re-created. The 15s "waiting for Sign in with Google" wait is skipped when an email/password Create Account or Sign In form is already present.
- **Create Account is a distinct scenario from Google login** and must not be reported as one. Both loops route a rendered Create Account form to `handleCreateAccount()` **before** the Google login path (`handleWorkdayLogin`); previously Manual mode fell through `isAuthenticationScreen()` into the Google flow and wrongly showed *"Sign in with Google is not available on this page."* `handleCreateAccount()` pre-fills the **known, non-secret email** (`fillKnownAuthEmail`, the configured account address — never a password, never auto-consent), then: Auto submits **Create Account** once the user has entered the password, re-entered it, and checked the consent box (`createAccountFormReady()`); Manual pre-fills the email and directs the user to Auto (Manual never originates account creation). The floating-panel subtitle is method-neutral — "Account: `<email>` (Google or email/password per tenant)" — not "Google account".

## State and isolation

- Workday code: `eve/workday.js`
- Narrow Google chooser: `eve/workday-google-auth.js`
- LinkedIn code remains in `eve/content.js`.
- Resume state is stored briefly in `chrome.storage.local` under `eveWorkdayAutoApplySession`, scoped to the exact Workday job/application path and considered stale after 30 minutes. Other application tabs on the same tenant cannot resume it.
- Workday personal information uses `workdaySavedAnswers`; LinkedIn continues to use `savedAnswers` and `savedRegexAnswers`. The stores never overwrite one another and are both included in Settings export/import.
